Bootstrap a Cosmos Hub testnet (`provider`) node in minutes instead of a multi-day full sync, in
**goleveldb** or **pebbledb**. Pick the database and the variant below - the table and the command
update together, so you always see exactly what you are about to download.

<Note>
  The testnet upgrades far more often than mainnet, usually to release candidates (for example
  `v28.0.0-rc0`). Always start the node on the `gaiad` version the network is running now - check
  [cosmos/testnets](https://github.com/cosmos/testnets/tree/master/provider) - not the mainnet release.
</Note>

<Warning>
  Do not skip the `priv_validator_state.json` backup step in the command. That file records the
  last height and round your validator signed. Restoring somebody else's signing state - or an
  older copy of your own - is the classic way to double-sign and get slashed.
</Warning>

## What's inside

- `data/` folder from a live Cosmos Hub testnet (`provider`) `gaiad` full node with pruning (`custom` / `keep-recent=100` / `interval=19`).
- `wasm/state` - the CosmWasm **contract bytecode**. `x/wasm` keeps only the code hashes in
  `application.db` and the bytecode itself on disk, so a `data/`-only archive restores a node
  that cannot execute contracts. It is bundled here so the snapshot is self-sufficient.
  `wasm/cache` is deliberately left out: it is a compiled, machine-specific cache your node
  rebuilds by itself.

Full archive listing: [snapshots.unitynodes.com/cosmos-testnet/](https://snapshots.unitynodes.com/cosmos-testnet/)

| Variant | Taken at | Use it when |
|---|---|---|
| **Latest** | every 4 hours | normal bootstrap of a node |
| **Pre-upgrade** | `H-1`, the last block before a scheduled upgrade height | you want to cross the upgrade yourself, on the old binary, exactly as the network does |
| **Post-upgrade** | shortly after the upgrade height, on the new binary | you are joining after an upgrade and want migrated state with no upgrade handling at all |
| **Wasm only** | same cadence as Latest | your node is already synced and you only need the CosmWasm contract bytecode |

## goleveldb or pebbledb

Every variant is published in both backends at the **same height**. The goleveldb snapshot is a cold
copy of the node's database; the pebbledb snapshot is converted from it and published only after
**every key and value** has been checked to match the goleveldb original.

<Note>
  A pebbledb snapshot needs **both** backend settings switched before the node starts - `db_backend`
  in `config.toml` and `app-db-backend` in `app.toml`. The pebbledb command below does it for you.
  Because the restore replaces the whole `data/` folder, this is also how you move an existing
  goleveldb node to pebbledb.
</Note>

<Warning>
  These are **pruned** snapshots. They are meant for validators, full nodes and RPC endpoints that
  only need recent state. They cannot serve historical queries - for that you need an archive node.
</Warning>

<Note>
  `pre-upgrade` and `post-upgrade` exist only around a scheduled testnet upgrade. Their tabs
  are greyed out until one is published, and each archive ships a `.txt` sidecar naming the
  upgrade it belongs to.
</Note>

## All restore commands

The same commands the picker above produces, in case you prefer them inline.

<CodeGroup>

```bash Latest (goleveldb)
sudo systemctl stop gaiad

cp $HOME/.gaia/data/priv_validator_state.json $HOME/.gaia/priv_validator_state.json.backup

rm -rf $HOME/.gaia/data
curl -L https://snapshots.unitynodes.com/cosmos-testnet/latest.tar.lz4 | lz4 -dc - | tar -xf - -C $HOME/.gaia

mv $HOME/.gaia/priv_validator_state.json.backup $HOME/.gaia/data/priv_validator_state.json

sudo systemctl restart gaiad && sudo journalctl -u gaiad -fo cat
```

```bash Latest (pebbledb)
sudo systemctl stop gaiad

cp $HOME/.gaia/data/priv_validator_state.json $HOME/.gaia/priv_validator_state.json.backup

rm -rf $HOME/.gaia/data
curl -L https://snapshots.unitynodes.com/cosmos-testnet/latest-pebbledb.tar.lz4 | lz4 -dc - | tar -xf - -C $HOME/.gaia

mv $HOME/.gaia/priv_validator_state.json.backup $HOME/.gaia/data/priv_validator_state.json

# pebbledb snapshot: switch BOTH backends before starting
sed -i 's/^db_backend = .*/db_backend = "pebbledb"/' $HOME/.gaia/config/config.toml
sed -i 's/^app-db-backend = .*/app-db-backend = "pebbledb"/' $HOME/.gaia/config/app.toml

sudo systemctl restart gaiad && sudo journalctl -u gaiad -fo cat
```

```bash Pre-upgrade (H-1)
sudo systemctl stop gaiad

cp $HOME/.gaia/data/priv_validator_state.json $HOME/.gaia/priv_validator_state.json.backup

rm -rf $HOME/.gaia/data
# goleveldb: pre-upgrade.tar.lz4   pebbledb: pre-upgrade-pebbledb.tar.lz4 (plus the two sed lines above)
curl -L https://snapshots.unitynodes.com/cosmos-testnet/pre-upgrade.tar.lz4 | lz4 -dc - | tar -xf - -C $HOME/.gaia

mv $HOME/.gaia/priv_validator_state.json.backup $HOME/.gaia/data/priv_validator_state.json

# start on the OLD binary - the chain will halt at the upgrade height, then swap and restart
sudo systemctl restart gaiad && sudo journalctl -u gaiad -fo cat
```

```bash Post-upgrade
sudo systemctl stop gaiad

cp $HOME/.gaia/data/priv_validator_state.json $HOME/.gaia/priv_validator_state.json.backup

rm -rf $HOME/.gaia/data
# goleveldb: post-upgrade.tar.lz4   pebbledb: post-upgrade-pebbledb.tar.lz4 (plus the two sed lines above)
curl -L https://snapshots.unitynodes.com/cosmos-testnet/post-upgrade.tar.lz4 | lz4 -dc - | tar -xf - -C $HOME/.gaia

mv $HOME/.gaia/priv_validator_state.json.backup $HOME/.gaia/data/priv_validator_state.json

# start on the NEW binary for that upgrade
sudo systemctl restart gaiad && sudo journalctl -u gaiad -fo cat
```

```bash Wasm only
# contract bytecode only - for a node that is already synced (either backend)
sudo systemctl stop gaiad

curl -L https://snapshots.unitynodes.com/cosmos-testnet/wasm.tar.lz4 | lz4 -dc - | tar -xf - -C $HOME/.gaia

sudo systemctl restart gaiad && sudo journalctl -u gaiad -fo cat
```

</CodeGroup>

## Verify (optional)

```bash
curl -fL -o snapshot.tar.lz4 https://snapshots.unitynodes.com/cosmos-testnet/latest.tar.lz4
curl -fL -o snapshot.tar.lz4.sha256 https://snapshots.unitynodes.com/cosmos-testnet/latest.tar.lz4.sha256
sha256sum -c snapshot.tar.lz4.sha256
```

For pebbledb use `latest-pebbledb.tar.lz4` and `latest-pebbledb.tar.lz4.sha256`.

## FAQ

<AccordionGroup>
  <Accordion title="How often is the snapshot updated?">
    goleveldb every **4 hours**; the pebbledb snapshot for the same height follows within about
    an hour. The last 2 of each are kept online.
  </Accordion>
  <Accordion title="What db backend?">
    Both. `goleveldb` and `pebbledb`, always at the same height.
  </Accordion>
  <Accordion title="How is the pebbledb snapshot produced?">
    It is converted from the goleveldb snapshot of the same height with
    [pebblify](https://github.com/Dockermint/pebblify), using the same pebble library version
    `gaiad` itself uses. Before anything is published, every key and value of the converted database
    is compared against the goleveldb original; a single mismatch stops the release.
  </Accordion>
  <Accordion title="Can I use this to bootstrap a validator?">
    Yes. The tarball carries only `data/` and `wasm/state`. There is no `config/` directory in
    it, so no `priv_validator_key.json`, no `node_key.json` and no keyring - your identity files
    are never overwritten by a restore.
  </Accordion>
  <Accordion title="Do I need to download the wasm archive separately?">
    No. `wasm/state` is already inside the snapshots above, so a single download gives you a
    node that can execute contracts. The standalone `wasm.tar.lz4` exists only for topping up a
    node that is already synced.
  </Accordion>
  <Accordion title="Is the node stopped while the snapshot is taken?">
    Yes, briefly. The goleveldb archive is a cold tar taken with `gaiad` stopped, so the database is
    never copied mid-write. The pebbledb conversion works on that finished archive and never touches
    the running node.
  </Accordion>
  <Accordion title="My pebbledb node prints `panic: pebble: closed` when I stop it. Is my data damaged?">
    No. On `gaiad` v28 with pebbledb, IAVL's background pruning can still be reading when the database is
    closed during shutdown, and pebble reports that as a panic where goleveldb would just return an error.
    It happens after the last block is already committed. We reproduced it on our own pebbledb node and
    restarted from the same data: the node reopened in 20 seconds and kept producing app hashes identical
    to independent public RPCs.
  </Accordion>
</AccordionGroup>
